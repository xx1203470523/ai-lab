# skill-gen 设计记录

> 标记：`[已确认]` 用户明确要求或确认 · `[建议]` AI 提议，待用户验收 · `[待确认]` 待用户决定 · `[推断]` 从现有实现反推
> 标记只用于设计结论。实现事实、验证结果和已读到的现状直接陈述，不加标记。
> 本记录创建于 2026-11-12 升级时。v1 实现早于本记录，凡从旧实现反推的内容标 `[推断]`。

## Part 1 Design Discovery

### 1. Problem

- [已确认] 旧版 skill-gen 解决的是"如何规范地生成 Skill"，缺少更前面的设计过程：用户只有一个模糊目标时，流程过早进入适用性、类型、目录和 SKILL.md 结构。
- [已确认] 典型例子："设计一个自动识别项目、理解需求、加载对应上下文的 Skill"。旧流程无法回答目标、触发场景、意图识别、输入上下文、内部行为、自主边界、人工确认点和验证方式。
- [已确认] 设计依据没有落盘，后续优化只能从实现反推，容易出现只改 SKILL.md、不改设计依据。
- [推断] 旧流程判断"是否已有技能覆盖"依赖临时浏览技能目录，没有固定检查方法，存在重复建设风险。

### 2. Goal

- [已确认] 从模糊想法出发，逐步完成问题理解、技能设计、方案讨论、验证和实现。
- [已确认] 每次创建或重构技能都有可追溯的设计记录；用户能围绕记录多轮讨论；确认后实现；实现后可复盘。
- [已确认] 价值判断：
  - 用户不需要预先提供完整设计，也能完成技能。
  - DESIGN.md 能解释关键取舍，而不是形式化填空。
  - 实现与已确认设计一致；不一致时有记录。
  - 问题能定位在设计层还是实现层。

### 3. Scope

负责 [已确认]：

- 技能需求发现与适用性判断。
- 新建、扩展、重构或不建的决策。
- 技能设计与设计验证。
- DESIGN.md 的创建与持续维护。
- 技能文件的生成和重构。
- 实现后的复盘与迭代记录。

不负责 [已确认]：

- 项目与任务管理（由 task-plan 等负责）。
- 知识库维护（由 knowledge-manage 负责）。
- 运行时调度、自动化执行引擎。
- 非技能场景的通用提示词设计。

边界 [建议]：

- 与 task-plan 无职责重叠：task-plan 规划工作，skill-gen 设计技能；skill-gen 不接管任务拆解。
- 与 knowledge-manage 无职责重叠：skill-gen 可按需读取知识作为上下文依赖，但不维护知识库。
- 与具体业务技能无重叠：skill-gen 只生成和改造它们，不替代其业务规则。

### 4. Usage Scenarios

应触发 [已确认]：

- "我想创建一个能分析项目上下文的 Skill。"
- "给现有 Git Skill 增加提交前检查能力。"
- "这个 Skill 的执行流程太复杂了，帮我重新整理。"
- "这个 Skill 经常误触发 / 该触发时没反应。"
- 显式调用 `/skill-gen`。

不应触发 [已确认]：

- "帮我执行一次 git status。"（一次性操作）
- 普通代码修改、知识问答、文档撰写。
- "帮我写一份周报模板。"（输出是文档，不是技能）

### 5. Expected Behavior

- [已确认] 默认走五阶段：Discovery → Design → Design Validation → Implementation → Review。
- [已确认] 用户只有模糊想法时，先理解目标和场景，不直接建文件。
- [已确认] 用户设计已明确时，允许快进到 Part 2，不重复大量需求澄清。
- [已确认] 用户提出重大变化时，先做影响分析，再局部更新设计，不覆盖全部文件。
- [已确认] 简单低风险技能允许快速模式，但仍建立 DESIGN.md 并标记未确认内容。
- [已确认] 阶段可以精简（减少问题、场景、章节），但不得跳过产出和门禁；只有快速模式允许合并阶段 1-4。
- [建议] 已有技能缺少 DESIGN.md 时，先读实现反推基线，全部标 `[推断]`，请用户确认后再继续。
- [建议] 用户拒绝设计确认时，停在 Reviewing，不生成正式技能文件。
- [建议] 设计与实现冲突时，以用户最新确认为准，并把差异记入 Part 3.4。

异常处理 [建议]：

- 技能目录不存在：按新建处理。
- 目标技能无 SKILL.md：先确认路径是否正确；确认后按新建处理。
- 多个现有技能职责重叠：列为 Open Question，由用户决定边界，不自行合并。
- 用户要求直接实现：给出最小设计摘要，取得明确确认并记录授权后再实现。

### 6. Input & Output

输入：

- [已确认] 用户的原始描述、补充说明和确认结论。
- [已确认] 现有技能目录、各 SKILL.md 的 description 与路由。
- [已确认] 目标技能的既有实现和 DESIGN.md。
- [建议] 项目上下文（CLAUDE.md、README、知识库）仅在设计需要时读取。

自动获取 vs 用户提供 [建议]：

- 自动：技能清单、现有结构、既有设计记录、项目背景。
- 用户：目标、使用场景、边界取舍、是否确认、是否覆盖已有文件。

输出：

- [已确认] `<skill-name>/DESIGN.md`，反映当前最新设计。
- [已确认] 确认后的技能文件（SKILL.md 及按需的 rules/workflow/reference/scripts）。
- [已确认] 设计摘要和 `[待确认]` 清单。
- [已确认] 验证与复盘记录。

### 7. Human Intervention

允许自主 [建议]：

- 读取文件和列出现有技能。
- 起草 Part 1/Part 2 和场景草案。
- 主动补充可能遗漏的场景，并标 `[建议]`。
- 做规范检查和文件结构建议。

必须确认 [已确认]：

- 是否值得建技能。
- 新建、扩展还是重构。
- 重大设计取舍和范围变化。
- 覆盖或删除已有技能文件。
- 把设计状态标为 Approved，把技能标为 Stable。
- 快速模式下是否立即生成初稿。

原因 [已确认]：这些决定影响用户的工作方式和已有资产；AI 无法替用户判断范围、优先级和可接受的风险。

### 8. Open Questions

- [待确认] 是否为除 skill-gen 外的现有 17 个技能目录批量补建 DESIGN.md？当前只在新建、重构或行为变更时要求。
- [待确认] 阶段 3 设计验证是否对所有业务型技能强制？当前建议必做；简单技能可以减少场景数量，但不能跳过验证。
- [待确认] 是否需要脚本检查 SKILL.md 与 DESIGN.md 的一致性？当前只靠流程约束。
- [待确认] 本目录不是 Git 仓库，"重要历史交给 Git"暂时不成立；是初始化 Git，还是长期依赖 Iteration History？
- [待确认] 新的 description 关键词是否合适？当前加入了修改技能、生成skill、create skill、design skill、refactor skill 等变体，需在真实使用中观察误触发和漏触发。

## Part 2 Skill Specification

### 1. Responsibilities

核心职责：

1. 判断需求是否适合做成 Skill，以及应新建、扩展、重构还是不建。
2. 引导用户从模糊目标形成结构化设计，并维护 DESIGN.md。
3. 发现并记录未确认、AI 建议和推断内容，不把它们伪装成结论。
4. 在设计确认后生成或改造符合约定的技能。
5. 用场景验证设计和实现，记录偏差与迭代。
6. 保留并复用原有规范：类型、命名、目录、模板、description、文件拆分、优化检查。

边界 [建议]：skill-gen 不执行的业务操作、不维护的知识和规划的任务，均不纳入职责。

### 2. Trigger Design

description [建议]：

> 设计和演进 Claude Code Skill。触发：新建技能、创建技能、写一个技能、设计技能、修改技能、优化技能、重构技能、生成skill、skill设计、梳理skill设计、skill误触发排查、create skill、design skill、refactor skill、/skill-gen。先用 DESIGN.md 理清目标、场景和设计并与用户确认，再生成或修改技能文件。

关键词覆盖 [建议]：

- 中文：新建技能、创建技能、写一个技能、设计技能、修改技能、优化技能、重构技能、生成skill、skill设计、梳理skill设计、误触发排查。
- 英文：skill、create skill、design skill、refactor skill、skill design。
- 显式：`/skill-gen`。

适用边界 [建议]：

- 只在涉及"创建、修改或设计一个可复用 Skill"时触发。
- 普通提示词设计、一次性命令、非技能文档任务不触发。

不适用场景 [已确认]：

- 执行一次 Git 操作。
- 普通代码修改或知识问答。
- 与技能无关的流程设计。

### 3. Workflow Design

| 阶段 | 输入 | 处理 | 输出 | 分支 / 异常 |
| --- | --- | --- | --- | --- |
| 1 Discovery | 用户描述、现有技能清单 | 复述目标 → 检查覆盖 → 适用性判断 → 梳理未知 | Part 1、建议与待确认清单 | 不建：说明原因直接处理；覆盖：转扩展/重构；模糊：只问 1-3 个关键问题 |
| 2 Design | Part 1、用户补充 | 按 9 个维度推进设计；多轮讨论 | Part 2 | 用户改想法：做影响分析后局部更新；缺信息：标 `[待确认]` |
| 3 Design Validation | Part 2 | 6 类场景推演与检查 | 场景记录、Part 2 修订 | 发现设计问题回到阶段 2 |
| 4 Implementation | Approved 的 Part 2 | 按结构生成/改造文件；复用模板和规范 | 技能文件、Part 3.1 | 用户未确认：不实现；实现与设计不符：改实现或先改设计 |
| 5 Review | 实际行为、设计场景 | 8 项检查；区分设计问题与实现问题 | Part 3 更新 | 实现问题改实现；设计问题回到阶段 2；未实测不得标 Stable |

门禁 [已确认]：

- 阶段 1 完成前不建实现文件；DESIGN.md 是例外，可以在发现阶段创建。
- 设计未确认前不覆盖正式实现文件。
- 阶段可精简，但产出和门禁不可跳过。
- 未实测不得标 Stable。

### 4. Context Dependencies

读取：

- `~/.claude/skills/` 的目录列表与各 SKILL.md description：判断覆盖与冲突。
- 存在项目级技能目录时（如项目内 `.claude/skills/`、`.ai/project/skills/`），一并检查。
- 目标技能的全部文件（SKILL.md、rules/、workflow/、reference/、scripts/）：优化与复盘。
- 目标技能的 DESIGN.md：设计依据。
- 项目 CLAUDE.md、README、knowledge：仅在影响技能设计时读取。

缺失、过期、冲突 [建议]：

- DESIGN.md 缺失：从现有实现反推 Part 1/Part 2，明确标 `[推断]`，请用户确认；反推只写 DESIGN.md，不改实现。
- 技能目录不存在：按新建处理。
- DESIGN.md 与实现不一致：以实现为准重建基线；差异写入 Design Deviations。
- DESIGN.md 的 updated 时间过旧：不直接信任，先对照当前实现。
- 多个技能职责冲突：不自行裁决，列为 Open Question 交用户决定。

### 5. Implementation Structure

[建议] 结构：

```text
skill-gen/
├── SKILL.md                       # 常驻：门禁、阶段表、分流、分类、生成底线
├── DESIGN.md                      # 本文件：设计依据与验证记录
├── reference/naming.md            # 命名规范
├── workflow/discovery.md          # 阶段 1
├── workflow/design.md             # 阶段 2 + 3
├── workflow/implement-review.md   # 阶段 4 + 5（含优化已有技能）
└── templates/
    ├── DESIGN.md.tmpl             # 通用设计记录模板
    ├── tool/                      # 工具型技能模板
    └── business/                  # 业务型技能模板
```

理由：

- SKILL.md 每次触发都会加载，只放门禁、阶段表、分流和底线。
- 阶段 1、2+3、4+5 各自有独立维护周期，拆成三个 workflow 文件。
- DESIGN.md 模板与技能模板放在一起，避免重复定义结构。
- `reference/naming.md` 保持原位置，不移动已有文件。

### 6. Tool Dependencies

- [已确认] 仅依赖基础文件读写、目录列举和文本检索。
- [建议] 支持选项式提问时（如 AskUserQuestion）优先使用，每次不超过 3 个问题；否则用普通提问。
- [已确认] 不依赖 Hook、Subagent 或脚本；没有自动化测试脚本。
- [建议] 上述依赖都可替换：选项式提问可退回普通提问，目录列举可用任意文件工具。

| 编号 | 决策 | 结论 | 标记 | 原因 | 影响 / 代价 |
| --- | --- | --- | --- | --- | --- |

| D2 | 设计记录位置 | 放在 `<skill>/DESIGN.md`，不做中央库 | [已确认] | 与实现同目录，便于同步和迁移 | 技能目录文件变多 |

| D4 | 内容标记 | 四类：已确认 / 建议 / 待确认 / 推断 | [已确认] | 需要区分"用户确认"和"AI 推断"，两者可信度不同 | 书写和阅读成本增加 |

| D7 | 快速模式 | 保留，但限定简单低风险技能 | [已确认] | 避免简单技能被五阶段拖累 | 需要判断风险和复杂度 |

| D9 | naming.md 位置 | 保留在 `reference/`，并由 SKILL.md 引用 | [建议] | 不移动已验证文件；修复旧版孤立引用 | 无 |
| D10 | "阶段可精简"的定义 | 减少问题、场景、章节数量；不跳过产出和门禁；只有快速模式可合并阶段 1-4 | [建议] | 旧表述"阶段可裁剪"没有边界，可能被理解为跳阶段 | 简单技能仍须保留 Part 1 结论、确认和记录 |
| D11 | 优化已有技能的入口 | 从诊断开始，不从阶段 5 开始；先读实现、建/核基线、区分实现问题与设计问题 | [建议] | 阶段 5 是"实现后复盘"，不能承担"诊断已有技能" | 入口多一个诊断步骤 |
| D12 | DESIGN.md 的定位 | 设计工作记录，不属于实现文件；发现阶段可创建或更新 | [已确认] | 否则"需求没理清不写文件"与"阶段 1 建 DESIGN.md"冲突 | 需要在约束中明确区分两类文件 |

### 3. Validation Results

结果：A-E 的预期行为全部满足，属于 L1 场景推演。

没有满足预期的地方：

- 无阻断性失败。所有代理都遵守了"未确认不写文件"。
- 场景 D 的代理判定 skill-gen 的 description 不应触发该请求，符合设计；这同时说明触发范围没有过宽。

发现的问题（已修复）：

1. 严重：阶段 4 的"或用户明确授权直接实现"与"未确认前不进入阶段 4"直接冲突。已统一为"必须 Approved；直接实现需先确认最小设计并记录授权"。
2. 严重："需求没理清不写文件"与"阶段 1 创建 DESIGN.md"冲突。已明确区分实现文件与设计工作记录。
3. 严重：优化入口写成"5 → 2"，但阶段 5 是实现后复盘，无法承担已有技能诊断。已改为"诊断 → 2 → 3 → 4"，并补充完整诊断流程。
4. 严重：未确认时不得覆盖的清单漏了 `reference/`、`templates/`。已补齐。
5. 中：discovery 缺少"扩展/重构但无 DESIGN.md"的分支。已补。
6. 中：discovery 步骤顺序存在循环（先引用第 3 步，再执行第 3 步）。已调整为先检查覆盖。
7. 中：`reference/naming.md` 自相矛盾（"无连字符"与带连字符示例；`wms-pda` 与实际 `wms-pda-dev` 不符）。已修正。
8. 中：业务型 SKILL.md 模板缺少"未匹配意图"兜底，与生成底线不一致。已补。
9. 中：变更影响分析表缺少"流程规则/模式/门禁"和"设计记录自身"两类，E 类变更会漏项。已补，并加入语义审计提醒。
10. 中：状态机没有重大变更回退规则；决策没有"被取代"写法。已补。
11. 低：description 缺少 create skill / design skill / refactor skill 等英文变体和"修改技能"等中文变体。已补。
12. 低：DESIGN.md 状态滞后于实现；"18 个技能没有 DESIGN.md"计数不准；Git 环境写死；模板占位语法未说明。均已修正。
