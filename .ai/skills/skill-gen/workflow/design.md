# 阶段 2：Skill Design

目标：把 Part 1 的问题转成可执行的设计。设计写进 DESIGN.md Part 2，不写实现文件。

开始设计时，把 DESIGN.md 状态从 Draft 改为 Reviewing。

## 设计顺序

按依赖关系推进，不按章节顺序填空：

1. **职责与边界**：负责什么、不负责什么、与哪些技能相邻。
2. **触发**：description、关键词、适用与不适用场景。
3. **行为**：主流程、条件分支、异常处理。
4. **输入输出**：自动获取 vs 用户提供；最终产物形态。
5. **上下文依赖**：项目背景、其他技能、知识库；缺失、过期、冲突时怎么办。
6. **人工介入**：可自动执行 vs 必须确认；原因。
7. **实现结构**：需要哪些目录和文件，按职责而非篇幅决定。
8. **工具依赖**：Hook、Subagent、脚本、外部工具；可替换性。
9. **设计决策**：重要取舍、备选方案、未采纳的原因。

每一项先写结论，再补必要依据；没有依据就标 `[待确认]`。

## 交互约定

- 用户可能不是专业设计者：先讲清"这个技能会怎么工作"，再谈术语。
- 一次只推进一个主题，最多 3 个问题。
- 主动补充用户可能遗漏的场景（误触发、缺输入、冲突），但标明 `[建议]`。
- 重要选择要给：推荐方案、理由、代价、替代方案。
- 不把 AI 的默认假设写成 `[已确认]`。
- 设计没理清前不写实现文件；用户催进度时，说明还缺什么，可以先给草案。
- 判断"够了"的标准：主要场景、输入输出、异常处理、人工介入点都有结论，且用户认可。

## 设计变更处理

用户改变想法时，先做影响分析，再改文档：

| 变化         | 需要复查                                               |
| ------------ | ------------------------------------------------------ |
| 目标/范围    | Part 1 的 Problem、Goal、Scope、场景                   |
| 触发方式     | description、关键词、误触发边界、与其他技能的重叠      |
| 主流程       | 行为分支、输入输出、异常处理、人工介入点               |
| 输入/上下文  | 依赖读取、缺失处理、过期与冲突策略                     |
| 实现结构     | 目录、文件拆分、脚本与工具依赖                         |
| 技术方案     | 工具依赖、可替换性、验证场景                           |
| 流程规则/模式/入口分流/门禁 | SKILL.md 的硬性约束、阶段说明、入口分流；对应 workflow 节；DESIGN.md 的 Workflow Design、相关决策、Part 3 实现记录和迭代史 |
| 设计记录自身 | Design Decisions、Implementation、Test Scenarios、Iteration History 是否仍与实现一致 |

重要变更要做语义审计，不能只搜关键词："可裁剪""快进""简化""2-3 个场景"等表述都可能是需要复查的旁路。

处理原则：

1. 只改受影响的部分，不重写整个文件。
2. 保留仍然有效的 `[已确认]` 内容。
3. 被推翻的结论改为 `[待确认]`，或移入 Design Decisions 记录取舍。
4. 被新版本取代的决策保留原文，标注"由 vN 取代"，不删除历史。
5. 改完告诉用户影响了哪些章节。

# 阶段 3：Design Validation

设计基本成形后（状态 Reviewing），用典型场景推演。

至少覆盖：

1. 正常输入。
2. 模糊输入。
3. 信息缺失。
4. 边界场景。
5. 误触发 / 漏触发。
6. 与现有技能冲突。

检查：

- 核心使用场景是否覆盖？
- 职责是否与现有技能重叠？
- 是否遗漏必要输入？
- 有没有无法处理的情况？
- 人工介入点是否合理？
- 输出是否能直接满足工作需求？

简单技能可以减少到 2-3 个代表性场景，但不能跳过验证。发现设计问题回到阶段 2 修改，不要带到实现阶段。

把场景写入 Part 3.2；实际行为没运行过就写"未实测"。

## 收尾：设计确认

1. 汇总设计摘要和 `[待确认]` 清单。
2. 明确询问用户：是否确认设计（Approved）？需要调整哪部分？
3. 用户确认后，把 `[建议]` / `[待确认]` 按决定改为 `[已确认]`，状态改为 Approved。
4. 未确认前不进入阶段 4。
