# 阶段 4：Skill Implementation

前置：DESIGN.md 状态为 Approved。

用户要求直接实现时，先给出最小设计摘要（目标、场景、行为、边界），取得明确确认，把状态记为 Approved 并注明"用户授权直接实现"，再开始。不得跳过设计记录。

## 执行

1. 按 Part 2 的 Implementation Structure 创建或修改文件，不额外加结构。
2. 生成 SKILL.md：参考 `../templates/tool/SKILL.md.tmpl` 或 `../templates/business/SKILL.md.tmpl`。模板中的 `{{占位}}` 和 `{{#each}}` 是待替换语法，必须替换为实际内容，不要原样写入。
3. 按需补充 rules/、workflow/、reference/、scripts/；每个文件只承担一种职责。
4. 更新 Part 3.1 Implementation，状态改为 Implementing；生成完成后改为 Validating。
5. 实现与设计不一致时：
   - 能按设计改就改实现。
   - 设计确实不合理，先改 Part 2：已经用户同意的标 `[已确认]`，尚未同意的标 `[待确认]` 并请用户确认；再改实现，并记入 Part 3.4 Design Deviations。

## 技能类型

| 类型   | 特征                                 | 命名              |
| ------ | ------------------------------------ | ----------------- |
| 工具型 | 确定性操作、无业务逻辑、跨项目复用   | `<name>`          |
| 业务型 | 领域知识、业务规则、协调多个技能     | `<business>-<module>` |

不要求严格二选一。按需补充属性：是否多步骤、是否需要脚本自动化、是否依赖业务知识、是否协调其他 Skill。命名见 `../reference/naming.md`。

## 内容取舍

只保留能影响 AI 行为的内容。以下属于有效内容，即使 AI 大体知道也可以写：

- 工作流步骤、执行顺序、条件分支
- 项目约束、业务规则、个人偏好、环境信息
- 输出格式、文件位置、字段要求
- 执行边界、禁止操作、决策标准

以下不写：通用知识教程、与执行无关的背景、重复强调、AI 每次都能自行推断的常识。

## 渐进式披露

- **SKILL.md**：核心规则、路由表、未匹配兜底。
- **workflow/**：多步骤流程，按阶段拆分。
- **rules/**：可独立加载的约束，适合按场景组合。
- **reference/**：领域知识、模板、参考配置。
- **scripts/**：需要确定性执行的自动化。

拆分依据（按顺序判断）：是否被多个行为复用 → 是否需要独立加载 → 是否有独立维护周期或版本管理。不要按行数机械拆分；几行且只服务一个上级文件的内容，留在上级文件里。

不制造空文件；不需要的目录不创建。只有必须保留目录结构时才用 `.gitkeep`。

## 目录结构

工具型：`SKILL.md`、`DESIGN.md`、`rules/`、`workflow/`、`reference/`（按需）。

业务型：`SKILL.md`、`DESIGN.md`、`rules/`、`workflow/`、`reference/`、`scripts/`（按需）。

## SKILL.md 结构

工具型：

- frontmatter：name、description
- 核心安全规则（始终有效，3-6 条）
- 路由表（命令 → 入口 → 说明）
- 未匹配命令兜底

业务型：

- frontmatter
- 协调规则
- 子技能路由（触发场景 → 入口）
- 安全规则

路由入口写相对路径 `./workflow/xxx.md`、`./rules/xxx.md`，与现有技能保持一致。

## 规则写作

标准：清晰、可执行、能改变 AI 行为。

- 一条规则只表达一个约束或一个步骤。
- 禁止空解释：无信息量的"由于…""可能…""建议尽量…"。
- 重要约束可以写简短原因、适用范围和风险，说明"为什么不能这样做"。
- 复杂流程允许分步骤写，不强行压成一行。
- 不用"强制""严格遵守"等修饰替代具体条件。

## description

- 中英混合关键词，覆盖用户常见叫法。
- 写明触发场景和适用范围，避免过宽。
- 关键词用 `、` 分隔，不用 `,`。
- 包含 `/skill-name` 作为显式触发。

## 优化已有技能

触发：用户要求改进、简化、重构或排查已有技能。先诊断，不要直接改文件。

### 1. 确认目标

- 用户没有指名技能时，先问是哪一个，不要猜。
- 读取该技能的全部实现：SKILL.md 及其引用的 rules/、workflow/、reference/、scripts/，必要时读 tests/。

### 2. 建立或核对设计基线

- 已有 DESIGN.md：逐项对照实现，标出不一致。
- 没有 DESIGN.md：创建 DESIGN.md（状态 Draft），从实现反推：
  - Part 1：从 description、路由和示例反推 Problem、Goal、Scope、Scenarios。
  - Part 2：从文件结构、规则和流程反推职责、触发、Workflow、依赖。
  - 无法确定的放进 Open Questions；所有反推内容标 `[推断]`。
- 反推只写 DESIGN.md，不改实现文件。

### 3. 诊断

检查：

1. 触发范围是否过宽或过窄。
2. 是否写了 AI 已知且不影响行为的内容。
3. 文件是否碎片化，或反过来过度堆积。
4. 规则是否含糊、重复、不可执行。
5. 是否有未匹配兜底。
6. SKILL.md 与 DESIGN.md 是否一致。
7. 职责、流程或边界本身是否合理。

区分问题层级：触发、内容、结构、一致性、流程。

### 4. 分派

| 诊断结果 | 动作 |
| --- | --- |
| 实现与设计不符 | 直接修实现，同步 DESIGN.md 的 Deviations 或 Iteration History |
| 纯文案、description 微调 | 直接修；有 DESIGN.md 就同步 |
| 职责、流程、触发或行为变化 | 按阶段 2 改设计 → 阶段 3 验证 → 用户确认 → 阶段 4 实现 |
| 目标或边界变化 | 回到阶段 1 |

### 5. 复盘

按阶段 5 检查实际效果，更新 Part 3。

# 阶段 5：Review & Iteration

技能实现后，用设计时的场景和真实使用反馈检查：

1. 是否正确触发。
2. 是否误触发。
3. 是否漏触发。
4. 是否按预期执行。
5. 异常处理是否正确。
6. 人工介入是否符合设计。
7. 输出是否满足工作要求。
8. 文件结构是否合理。

判断责任：

- 实现不符合设计 → 改实现。
- 设计本身有问题 → 先改 DESIGN.md，再改实现。
- 两者都没问题但效果不好 → 补场景，重新评估设计。

验证可信度：

| 级别 | 含义                                     | 可支撑的状态          |
| ---- | ---------------------------------------- | --------------------- |
| L1   | 只做场景推演，未实际运行                 | Reviewing / Validating |
| L2   | 实际调用过 1 个场景                      | Validating            |
| L3   | 覆盖正常、模糊、缺失、异常多个场景       | Validating，可申请 Stable |
| L4   | 真实使用一段时间，无阻塞问题             | Stable                |

一次成功不等于完整验证。任何未实测的内容必须如实写出，不得标 Stable。

更新 Part 3：Validation Results、Design Deviations、Iteration History（仅重要版本）、Current Limitations、Next Improvements。

## 快速模式

适用于：单一用途、无业务规则、无现有技能冲突、低风险。

1. 用 1-2 个问题确认目标和触发场景。
2. 直接生成初稿 + DESIGN.md（状态 Draft）。
3. 在 Open Questions 和相关章节标注 `[待确认]`。
4. 明确告诉用户哪些内容未确认、未实测。

快速模式不用于业务型技能、会改变现有行为的重构、涉及脚本或外部系统的技能。
