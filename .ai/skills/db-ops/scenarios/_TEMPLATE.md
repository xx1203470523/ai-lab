# 场景剧本模板

复制本文件到 `scenarios/<slug>.md`（通用剧本）或 `references/projects/<name>/scenarios/<slug>.md`（项目专属），按下面各段填写。

**只写你真正排查过的。** 没跑过的剧本必须写 `状态：未验证`，并且在使用时降级为一次普通排查——不得拿它当结论依据（见 `workflows/troubleshoot-flow.md`）。

```markdown
# <一句话说明这是什么问题>

状态：已验证 | 未验证
最后验证时间：YYYY-MM-DD
适用项目：<项目名 | 通用>
涉及路由：<路由 id，可多条；写清是"这些路由上都可能出现"还是"只在某条上">

## 识别条件

- 症状：<使用者会怎么描述这个问题——用他/她的话，不要用术语>
- 报错/关键输出：<原文，可模糊部分用 …；没有报错就写「无报错，只是数字不对」>
- 涉及对象：<单据类型/标签/物料/表>
- 可复现条件：<在什么前提下必然出现>

命中**主要**条件才套用；只沾一条不算。拿不准就按普通排查走。

## 为什么会出现

<机理。这一段是剧本的价值所在——只说"这么查"而说不出"为什么会这样"的剧本，
 下一次现象稍有变化就失效。>

## 诊断 SQL

每条前面写清它在问什么。查询必须只读、单库、带收窄条件。

```sql
-- 问：<这条在验证什么>
SELECT ...
```

## 判定

| 诊断结果 | 结论 |
|---|---|
| <结果 1> | <成因 / 处置方向> |
| <结果 2> | <成因 / 处置方向> |
| 都不符合 | 这是新情况：按普通排查继续，并考虑更新本剧本 |

## 处置

- 只读能解决的：<具体动作>
- 需要改数据：转 `workflows/exec-flow.md` 的受控执行流程，**不在本剧本里顺手写库**。

## 回滚

<如果处置涉及写操作，回滚语句是什么；纯只读则写「不涉及」。>

## 验证

<处置后重跑哪条诊断语句、期望看到什么。>

## 残留不确定性

<哪些结论是推出来的而不是直接看到的；什么情况下本剧本会失效。>
```

## 写剧本的几条硬要求

- **诊断语句要能独立读懂**：每条只回答一个问题，不要一串 SQL 只给一个结论。
- **不写「大概」「应该」**：验证过的写事实，没验证的写进「残留不确定性」。
- **不留凭据**：`sql/` 与 `scenarios/` 会进版本库，注释里也不要放口令。
- **给结果留位置**：判定表必须包含「都不符合」这一行——否则剧本会诱导人把新问题硬套成旧问题。
- **升级剧本时同步改「最后验证时间」**，否则下一个人无法判断它是否还有效。
