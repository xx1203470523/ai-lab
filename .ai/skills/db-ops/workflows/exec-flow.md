# 受控写执行流程（`-Mode Exec`）

**状态：已实现，但只覆盖「单条写语句 + 摘要确认 + 事务」。** 自动备份、影响行数上界预估、执行后验证与独立审计尚未实现。
因此当前只应在开发库使用 `Exec`；正式库的写操作继续走「生成 SQL → 人工在数据库客户端执行」。

## 为什么写操作要单独一层

只读层的守卫对写操作**完全不适用**：写操作的目的就是改数据，关键字拦截没有判据。
写操作的安全性只能来自**流程本身**：执行前让人看到「对哪个库、执行哪句 SQL」，并让确认与这段原文绑定。

## 前置（缺一不可）

1. 用户**明确**要求改数据，并说清对象与目的（不是「顺手改一下」）。
2. 目标路由的 `effectiveStatus` 是 `ready`。
3. `policy.exec.allowWrite = true` 且该路由 `allowWrite = true`。
4. 影响面已量化：目标表、条件、预计影响行数上界、是否有外键/触发器/同步链路的连带影响。

## 步骤

### 1 影响面分析（只读）

先用 `Query` 把「将要被改的行」查出来：条件一致、只查主键与关键列、带 `LIMIT` 看规模。

- 影响行数与预期不符 → **停**，先解释清楚差异。
- 涉及生产库的批量改动 → 先把影响面报告给用户；正式库当前不通过 `Exec` 执行。

### 2 生成计划：不带 `-Confirm` 先跑一次

```powershell
powershell -NoProfile -File "$sk\db-ops.ps1" -Mode Exec -Target dev.lebgjm -Sql 'UPDATE ...'
```

脚本**不执行**，只打印计划并 `exit 3`：

- 路由、库名、掩码后的账号、语句类型；
- SQL 原文；
- 确认摘要（`Get-Sha256Short`，16 位）。

摘要的输入是「路由 id + 库名 + SQL 原文」。任何一处变化（哪怕改一个字符）都会让摘要失配，必须重新确认。这是防止「确认的是 A、执行的是 B」的唯一手段。

### 3 显式确认

把第 2 步的计划与 SQL 原文给用户核对。用户明确同意后，把摘要原样传回：

```powershell
powershell -NoProfile -File "$sk\db-ops.ps1" -Mode Exec -Target dev.lebgjm -Sql 'UPDATE ...' -Confirm <摘要>
```

退出码：

| 码 | 含义 |
|---|---|
| `0` | 已执行 |
| `1` | SQL 不是写语句（应走 `Query`），或一次给了多条语句 |
| `3` | 缺少 `-Confirm`，只打印计划 |
| `4` | 摘要不匹配，未执行 |
| `5` | 路由未 ready，或全局/路由写闸门关闭 |

**不提供** `-Force` / `-Yes` / `--non-interactive` 之类的免确认开关。

### 4 事务

- JDBC 驱动：`autoCommit=false`，执行成功后 `commit()`；抛异常则 `rollback()`。
- mysql CLI 驱动：单条语句由数据库自身保证原子性，但没有显式事务边界。
- `Exec` **只接受一条语句**，避免「一半成功一半失败」的半成品状态。

### 5 尚未实现（不要假装有）

- 执行前把将被修改的行导出为可回滚备份；
- 影响行数上界预估；
- 执行前后各跑一次验证语句并对比；
- 独立审计日志（当前只有命令行输出与 JSON 信封里的 `Details`）。

在这些补齐之前，正式库写操作继续按下节执行。

## 正式库的等价做法

1. 用只读流程（`Query`）做影响面分析；
2. **生成**写 SQL（不执行）；
3. 把 SQL、影响面、回滚语句、验证语句交给人在数据库客户端里执行；
4. 按 `sql/README.md` 归档，含回滚与验证说明。

生成 SQL 时**不要把凭据写进 SQL 文件**，也不要在 SQL 注释里留口令——`sql/` 是会进 Git 的。

## 禁止

- 禁止在 `Query` / `File` 里执行写语句（会被守卫拒绝，不要试图绕过它）。
- 禁止跳过影响面分析直接执行。
- 禁止用「先改开发库验证过了」当作生产库免确认的理由（开发库与生产库的差异正是风险所在）。
- 禁止在冲突、超时或摘要不匹配时「重试一次」——重试意味着绕过了确认链。
