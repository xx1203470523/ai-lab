# 受控写执行流程（`-Mode Exec`）

**状态：阶段 1 未实现。** `exec.allowWrite = false`，`-Mode Exec` 只会明确报「阶段 2 未实现」并 `exit 1`。
本文件是**设计契约**：它描述写操作允许长什么样。阶段 2 按此实现，实现前不得以任何形式绕过。

## 为什么写操作要单独一层

只读层的守卫（关键字拦截 + 只读账号）对写操作**完全不适用**：写操作的目的就是改数据，拦截器没有判据。
因此写操作的安全性不能来自「拦得住」，只能来自**流程本身**：先看到计划，再确认，再在事务里执行，出问题能回滚，事后有审计。

## 前置（缺一不可）

1. 用户**明确**要求改数据，并说清对象与目的（不是「顺手改一下」）。
2. 目标路由的 `effectiveStatus` 是 `ready`，且**账号是该库的写账号**——只读账号执行写操作应当被数据库拒绝；被拒绝了不要去找别的账号。
3. `policy.exec.allowWrite = true`（默认 false，需要人工改策略文件，这是一道**刻意的手工闸门**）。
4. 影响面已量化：目标表、条件、**预计影响行数上界**、是否有外键/触发器/同步链路的连带影响。

## 步骤

### 1 影响面分析（只读）

先用 `Query` 把「将要被改的行」查出来：条件一致、只查主键与关键列、带 `LIMIT` 看规模。
- 影响行数与预期不符 → **停**，先解释清楚差异。
- 涉及生产库的批量改动 → 先把影响面报告给用户，等确认再进下一步。

### 2 生成计划与摘要（PlanDigest）

计划内容包括：目标路由、库名、语句（单条或多条有序语句）、条件、影响行数上界、备份方式、回滚语句、验证语句。
对计划内容算一个摘要（`Get-Sha256Short`）作为 `PlanDigest`。

**摘要的意义**：确认的是「这一份计划」，不是「这类操作」。计划在确认之后被改动（哪怕改一个字符），摘要就对不上，必须重新确认。这是防止「确认的是 A、执行的是 B」的唯一手段。

### 3 显式确认

- 确认必须由人给出，且**必须是针对该摘要**的确认。
- 退出码：没有摘要 → `3`；摘要不匹配 → `4`；需要确认 → `2`。
- **不提供** `-Force` / `-Yes` / `--non-interactive` 之类的免确认开关。非交互环境里执行写操作 = 直接拒绝。

### 4 备份 / 可回滚性

- 执行前把将被修改的行导出为可回滚的形式（含主键与原值），落到 `policy.temp` 指定的目录。
- 无法回滚的操作（`DROP`、`TRUNCATE`、无主键表的批量 `UPDATE`）**一律拒绝**，不通过「用户说可以」来放行——这句话在事后无法复原任何东西。

### 5 事务执行

- 默认**单事务**：全部语句一起提交，任一条失败即整体回滚。
- 必须分批时，每批单独提交并记录批次边界，且每批都要有可回滚依据。
- 执行前后各跑一次验证语句（同一条件各查一次），把**实际影响行数**记下来。

### 6 验证与回滚

- 验证语句的结论与预期不一致 → 立即回滚，并报告回滚结果（回滚失败要升级为故障，不是「尽力了」）。
- 提交之后再发现问题：用第 4 步的备份反向生成恢复语句，**仍然按本流程重新确认**（恢复也是一次写操作）。

### 7 审计

记录：时间、目标路由与库名、语句摘要、`PlanDigest`、影响行数、确认方式、结果、回滚情况（如有）。
日志里**不得**记录凭据值；`logging.storeQueryText` 默认 false 时只记摘要，不记 SQL 原文。

## 阶段 1 的等价做法（唯一允许）

技能不执行写操作。允许的路径是：

1. 用本流程的 1–2 步做影响面分析（只读，可以用 `Query`）；
2. **生成**写 SQL（不执行）；
3. 把 SQL、影响面、回滚语句、验证语句交给人在数据库客户端里执行；
4. 按 `sql/README.md` 归档，含回滚与验证说明。

生成 SQL 时**不要把凭据写进 SQL 文件**，也不要在 SQL 注释里留口令——`sql/` 是会进 Git 的。

## 禁止

- 禁止在 `Query` / `File` 里执行写语句（会被守卫拒绝，不要试图绕过它）。
- 禁止跳过影响面分析直接执行。
- 禁止用「先改开发库验证过了」当作生产库免确认的理由（开发库与生产库的差异正是风险所在）。
- 禁止在冲突、超时或摘要不匹配时「重试一次」——重试意味着绕过了确认链。
