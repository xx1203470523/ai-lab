# 场景剧本排查流程

适用：同一类问题**重复出现**（「又是这个」「上次也这样」），或问题时常见到值得沉淀成剧本。

单次、一次性、没有复发迹象的问题**不要**写成剧本——剧本的成本在于维护，只有复用的收益能抵过它。

## 剧本从哪来

优先级从高到低：

1. `references/projects/<name>/scenarios/` — 项目专属剧本（例如 WMS 的软删除判定）。
2. `scenarios/` — 与项目无关的通用剧本（例如「连不上库」「查询超时」这类跨项目问题）。
3. 都不命中 → 按下面的流程当场排查，并在收尾时判断「这个问题值不值得升级成剧本」。

**只有被真实排查验证过的剧本才算数。** 未经真实库验证的剧本必须显式标注 `状态：未验证`，并且在给结论前先降级为一次普通排查——不要拿未验证的剧本当结论依据。

## 排查步骤

### 1 识别条件

对照剧本的「识别条件」段，判断是否命中：症状、报错关键字、涉及的业务对象、可复现的条件。
命中一条不足以套用剧本，应当命中**主要条件**；拿不准就按普通排查走。

### 2 收窄到一条路由

先定目标路由并看状态（见 `query-flow.md` 的 1–2 步）。**目标不是 `ready` 就停**——在错的库上排查，找到的「证据」比没有证据更糟。

### 3 跑只读诊断

按剧本列出的诊断语句逐条执行，**每条都记录结果**（哪怕是 0 行）。不要一次跑一堆然后只报结论：中间结果正是判断分叉的依据。

### 4 判定

对照剧本的「判定」段得出结论，并区分三种情况：

- 命中已知成因 → 给出结论 + 依据（哪条诊断语句的哪一行结果）。
- 命中剧本但结果不符合任何已知成因 → **这是新情况**，按普通排查继续，并考虑更新剧本。
- 完全不命中 → 回到普通排查，不要在剧本上硬套。

### 5 处置

- 只读能解决的（补查、纠正口径、指出配置问题）→ 直接给结论。
- 需要改数据 → 转 `exec-flow.md`，**不在本流程里顺手写库**。
- 处置后必须**验证**（同一条诊断语句再跑一次），并把验证结果写进报告。

### 6 沉淀

- 新成因、新诊断语句、新边界 → 更新剧本，同时更新它的「最后验证时间」。
- 剧本中的 SQL 如果通用性强，按 `sql/README.md` 归档一份。

## 输出

一份排查报告至少包含：症状、目标路由与库名、跑过的诊断语句（可摘要）、**关键结果**、判定与依据、处置动作、验证结果、以及残留不确定性。

- 不确定就写不确定。把「没查到」写成「不存在」是本流程最严重的错误。
- 排查过程里发现的范围外问题：记录到报告末尾，**不顺手改**。

## 禁止

- 禁止跨库「顺手都查一遍」凑证据。
- 禁止把未验证的剧本结论当成事实。
- 禁止用近似路由或未确认的据点去跑诊断。
