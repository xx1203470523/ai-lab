# Task Ready

## Scope

只检查用户当前任务描述是否足以进入 Plan Mode，以及是否存在少量容易导致返工的关键遗漏。保持语言无关；简单且确定的局部任务直接放行，不进行过度检查。

Task Ready 回答“我要做什么、有没有关键内容没说”；Plan Mode 回答“知道要做什么后怎么实现”。本 Skill 是提示级输入检查，不是 Plan Mode、需求编译器、审批器或强制安全边界。

## Constraints

- 复杂任务先检查四个基础维度：Goal（最终问题或结果）、Scope（允许修改到哪里）、Behavior（哪些行为改变、哪些必须保持）、Constraint（明确不能做什么）。四维不要求用户使用正式标签。
- 重点任务包括重构、优化、重写、解耦、架构调整、页面改造、UI 与业务流程、新增完整业务流程、跨模块/跨端、数据库变化、数据迁移、删除/替换逻辑和多步骤业务任务。
- 若缺失的信息会迫使 AI 替用户决定产品目标、业务规则、行为兼容性、修改范围或数据语义，判定 BLOCK，输出 NOT READY；若只是容易遗漏但不阻碍进入 Plan Mode，输出 READY + WARNING。
- 不要要求文件路径、类名、方法名、调用链、当前代码结构、页面结构、API 实现、Service 拆分方式、技术选型或可由代码和既有约定推断的细节。
- 不要把未列出所有异常情况当作阻塞。若用户已明确“按现有逻辑”，不要重复询问代码可以确定的按钮、状态、入口、错误处理或详情行为。
- 涉及 UI、业务流程、状态、接口或数据时，重点确认行为改变/保持项；仅写“优化体验”而未说明提交、成功后、失败后、审核、详情或状态行为时，若这些会改变结果则 BLOCK，不得自行补规则。
- Scope 必须能判断其他业务模块、公共组件、基础设施、数据库和接口契约是否允许修改；防止“顺便优化”扩大范围。
- 本 Skill 只使用用户当前 Prompt 和其中明确提供的上下文，不读取仓库代码，不运行命令，不修改文件，不生成 Plan，不拆任务，不审批，不执行，不替代 task-planner、task-plan、task-spec、task-execute 或 Plan Mode。
- 不要把 task-spec 的 approval、Plan Package、revision、hash 或 task-execute 路由引入本输入检查。

## Gap Check

仅对复杂任务执行有限的风险遗漏检查；不列完整检查清单，只输出最可能导致实现偏差的 1–3 项。

- **UI / 页面**：关注入口与操作路径、输入校验、按钮状态、提交、成功/失败后行为、刷新/列表状态、返回/取消、权限和状态变化。代码已有且用户要求沿用的行为不重复问。
- **新增或修改业务接口**：关注输入校验、查询规则、重复数据、异常与返回结果、上下游兼容、事务和状态更新。只提醒无法从现有约定确定且会影响结果的事项。
- **重构**：关注业务规则、输入输出、状态流转、API/数据结构兼容，以及公共模块、相关模块和无关问题是否允许修改，防止技术重构变成业务重写。
- **数据库 / 数据迁移**：关注新旧数据、默认值、NULL、历史数据、兼容性、索引、回滚和上下游影响；只暴露需要用户决定的高风险缺口。
- **其他复杂任务**：根据用户明确的任务类型检查一个最相关的前置、后置、成功、失败、重复、权限、状态或一致性事项，不机械套用全部清单。

发现遗漏时只暴露问题，不替用户选择。例如应问“重复编码已存在时是忽略、更新还是报错？”，不能自行决定覆盖。

## Decision

1. 判断是否为简单、局部、确定任务；是则直接 READY。
2. 否则检查 Goal、Scope、Behavior、Constraint。
3. 对已满足基础边界的复杂任务执行 Gap Check；能由代码或用户已给出的“现有逻辑”确定的内容跳过。
4. 将结果分级：关键缺失为 BLOCK；非关键但高概率返工的缺口为 WARNING；没有重要缺口则无附加内容。

## Output

### 无问题

```text
READY
```

### 有非阻塞遗漏

```text
READY
WARNING:
1. <最重要的遗漏问题>？
2. <必要时再列 1–2 项>？

以上仅为可能遗漏项，不回答也可以继续。
```

### 有关键缺失

```text
NOT READY
1. <必须确认的问题>？
2. <必要时再列问题>？
```

问题默认 1–3 个，绝不超过 5 个。排序优先级为业务逻辑错误、UI 操作流程错误、范围扩大、数据问题、兼容性问题、其他低风险细节。

## Validation

- READY 只输出 READY，最多附一句极短说明；没有 WARNING 时不要补充分析。
- WARNING 只能出现在 READY 之后，最多列 1–3 个最可能导致返工的非阻塞问题，并明确“不回答也可以继续”。
- NOT READY 只能列真正必须用户回答的问题，禁止把 WARNING 混入其中。
- 禁止重写 Prompt、自动补充业务规则、替用户做产品决策、输出详细技术方案、Plan、代码扫描、代码或实现建议。
- 不因缺少文件位置、技术方案或代码细节机械拦截；不要求用户穷举所有异常情况。
- 人工评估至少覆盖：`重构送检模块` → NOT READY；目标/范围/行为/限制清楚的复杂重构 → READY；明确 BomCode 手动/自动行为的小修改 → READY；“优化送检页面让提交更方便”但提交及成功后行为未决 → NOT READY；明确新增供应商手动同步但未决定重复数据处理或成功后刷新 → READY + WARNING；仅缺文件路径或技术方案但边界清楚 → READY；查看/定位/解释代码 → 不触发本 Skill。
