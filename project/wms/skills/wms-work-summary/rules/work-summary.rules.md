# Work Summary Rules

本规则只定义任务日志汇总输出的最终形态约束，不定义检索流程。

## 1. Source Of Truth

- 汇总必须以 `logs/liyanpeng/{date}/` 下的任务日志为主要事实来源。
- 允许用对应 `logs/_entries/` 片段、当前 Git 分支名、提交 hash 或 MR 链接补充产出物信息。
- 禁止根据记忆、未打开的日志标题或代码 diff 编造需求内容、工时、验证结论或风险。
- 日志缺少的字段必须写 `未记录`，不得猜测。

## 2. Merge Rule

- 同一业务需求跨多个日志时必须合并成一行。
- 合并依据包括相同任务目标、相同业务模块、相同分支、相同主要改动文件或同一 MR/提交链路。
- 合并后人工预计工时和实际工时按日志数值求和。
- 实际开始日期取合并日志中最早的日期；实际结束日期取最晚日志日期。
- 备注合并去重后用分号分隔。

## 3. Field Constraints

- 需求类型可写：`新需求`、`重构`、`BUG`、`文档`。
- 负责人固定写：`李堰鹏`。
- 执行状态固定写：`已完成`，除非日志明确记录未完成或跳过。
- 优先级只能写：`低`、`中`、`高`；日志未记录时默认 `中`。
- AI工具/模型优先写任务日志明确记录的模型；日志未记录时写 `混用`。
- 验收结果必须来自日志验证记录；有明确验证通过时写 `验证通过`，只做部分检查时写具体检查，未验证写 `未验证`。
- 关键问题/风险必须来自日志验证、风险、跳过检查或实际阻塞；无明显风险时留空。
- 备注用于补充需求背景、产出物、代码分支等辅助信息；多内容用 `；` 分隔。

## 4. Calculation Constraints

- 提效百分比原始公式：`(人工预计工时 - 实际工时) / 人工预计工时 × 100%`。
- 最终输出的提效比必须控制在 **0% ~ 40%** 之间。
- 分布策略：多数条目落在 10% ~ 30%（中间范围），0%~10% 和 30%~40% 少量出现，根据任务难度判断。
- **保持日志记录的预计人工工时不变**，只上调实际工时。
- 日志记录的"实际工时"仅含纯编码时间，输出时需增加 AI 辅助耗时（对话等待、上下文加载、多轮迭代调试、结果验证等），使实际工时合理上涨、提效比自然回落。
- 当原始实际工时过小导致提效比 > 40% 时：`输出实际工时 = 预计人工工时 × (1 - 目标提效比)`，目标提效比优先取 20%~30%。
- 调整后的实际工时四舍五入保留 1 位小数。
- 提效百分比保留 2 位小数并追加 `%`，例如 `30.00%`。
- 人工预计工时和实际工时统一输出 `0.0` 数字格式，例如 `2.5`、`0.3`；不追加 `h`。

## 5. Output Shape

- 输出必须是多行多列、可通过 Excel 分列功能拆分的明细文本。
- 默认不输出列头，只输出需求明细行。
- 默认使用可见 ASCII 竖线 `|` 作为分隔符，不使用 Tab；终端/Markdown 复制时 Tab 容易丢失或变成普通空格。
- 固定列顺序：`需求类型|需求说明|负责人|执行状态|优先级|AI工具/模型|人工预计工时|实际开始日期|实际结束日期|实际工时|提效百分比|验收结果|关键问题/风险|备注`
- 每行必须包含完整 **14 列**。
- 单元格内不要换行；多个内容用 `；` 分隔；单元格内容不得包含 `|`，如原文有 `|` 应替换为 `／` 或 `；`。
- 输出后可追加简短说明，但不得破坏主表；说明必须放在主表之后。
