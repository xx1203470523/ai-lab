# Scoped Batch Planning Workflow

本 workflow 用于 `/wms-dev` 在写代码前控制“这次应该只改多少”。

核心目标：先做宽而浅的综合评估，再只对用户选择或明确推荐的批次深分析和实现，避免一次性深挖或修改 P0-P3 全部候选。

## Gate Timing

- 本 workflow 的综合评估、Task Contract 草案、推荐执行批次和后续候选属于只读阶段，不要求 `/wms-start-gate`。
- 用户确认某个批次并准备写文件时，才进入 `/wms-start-gate`。
- gate 未通过时，不得把草案升级为实现计划。
- 验证、跑代码、build/test 前只确认 `origin/main` 基线，不重新执行完整 start gate。

## Output Mode

- 小改动默认使用轻量输出，只保留 Mini Task Contract、处理建议、验证与清理和 Blocked 信息。
- 多层联动、优化/重构合集、契约影响或多批次候选时才使用完整输出。
- 不得为了套完整模板而生成空表格；没有候选就不要输出综合候选表。

## 1. 综合改动范围评估

先用有限上下文输出候选范围，不把所有候选都深挖为实现计划。

评估表必须包含：

| 优先级 | 类别 | 改动项 | 涉及文件数 | 风险 | 证据等级 | 建议分支范围 |
|---|---|---|---|---|---|---|
| P0 | ... | ... | ... | ... | 已确认 / 部分确认 / 估算 / 粗评估 | 本次优先做 / 单独分支 / 后续候选 |

证据等级含义：

- 已确认：已读过目标逻辑和必要调用链，可以进入本批次实现计划。
- 部分确认：已确认主路径，但消费者、边界或异常分支未完全确认。
- 估算：基于局部代码、命名或结构推断，未深读完整逻辑。
- 粗评估：仅作为架构或后续优化候选，不进入本次实现。

## 2. Task Contract

进入实现前必须先形成 Task Contract，用来锁定本次分支和本次提交的边界。

Task Contract 至少包含：

```markdown
## Task Contract

- 本次批次：P0 / P1 / P1-Contract / P2 / P3
- 本次目标：...
- In Scope：...
- Out of Scope：...
- 明确不改：...
- 允许读取：...
- 禁止读取 / 修改：...
- 涉及层级：Entity / Repository / Service / Controller / DTO
- 预计文件数：...
- 契约影响：无 / API / DTO / Web / PDA / 打印 / 导出 / 外部系统
- 需要用户确认：...
- 验证方式：...
- 停止条件：...
```

如果无法明确 In Scope / Out of Scope，任务状态必须进入 `Blocked`。

## 3. 推荐执行批次

默认推荐从收益最高、风险最低、文件最少的批次开始。

优先级定义：

- P0：明确 bug、低风险、文件少、契约不变、收益直接。
- P1：中风险逻辑修复或局部重构，可能影响调用链。
- P1-Contract：DTO / API / Web / PDA / 打印 / 导出 / 外部系统契约相关，必须单独确认消费者影响。
- P2：方法抽象、查询统一、重复逻辑收敛、局部结构优化。
- P3：职责拆分、架构调整、新 Service / 新模块或跨层改造。

推荐输出必须说明：

- 建议本次分支只处理哪一个批次。
- 为什么不把其他批次混入本次分支。
- 如果用户不同意推荐批次，等待用户选择后再深入。

## 4. 批次升级与越界阻断

实现过程中如果发现当前批次会升级风险，必须停止并重新确认。

常见升级：

- P0 逻辑修复需要改 DTO / API 契约 → 升级为 P1-Contract。
- P0 / P1 逻辑修复需要跨 Service / Repository 大范围抽象 → 升级为 P2。
- P2 方法抽象需要新建职责类、拆 Service 或调整入口路由 → 升级为 P3。
- 任意批次影响 Web / PDA / 打印 / 导出 / 外部系统消费者 → 至少升级为 P1-Contract。

升级后处理：

1. 停止当前实现。
2. 输出越界原因和新增影响范围。
3. 更新 Task Contract。
4. 等待用户确认是否继续、拆分新分支或降级只做原批次。

## 5. 后续候选

未进入本次批次的候选必须保留为摘要，不继续深挖消耗上下文。

输出格式：

| 优先级 | 候选项 | 当前证据等级 | 不在本次处理原因 | 建议后续分支 |
|---|---|---|---|---|
| P1 | ... | 部分确认 | 需要调用链确认 | fix/lyp/... |

后续候选只做索引，不作为本次实现许可。

## 6. Token 控制原则

- 综合评估阶段只做宽而浅的范围判断。
- 只有被选中的批次进入深读、调用链分析和实现计划。
- 未选中的 P1 / P2 / P3 只保留候选摘要。
- 不为了“顺手优化”读取或修改本次 Task Contract 外的文件。
